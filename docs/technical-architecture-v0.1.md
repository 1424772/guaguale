# 技术架构 v0.1

> 状态：首版可运行基线。账号、金币、卡 1–6、每日恢复、互动桌面、好运、刮奖范围、垃圾桶和固定卡槽商店均已实现；后续接入机器人、风扇与卡 7–8。

## 1. 技术栈

- Web：React 19、TypeScript、Vite、Canvas 2D。
- API：Go 1.26，标准库 HTTP 路由。
- 主数据：MySQL 8.4，账户余额、金币流水、会话和卡片均以 MySQL 为最终事实来源。
- Redis：限流、热点排行榜、短期幂等缓存与分布式协调；不作为金币余额的最终来源。
- 部署：Docker Compose、Nginx，同源 `/api/v1` 访问。

## 2. 服务端边界

- 浏览器只提交操作意图并播放动画，不生成奖项、不直接修改余额。
- 购卡时，服务端在数据库事务中锁定用户余额、扣款并生成不可变开奖结果。
- 刮开接口只把已经生成的结果公开给用户；刷新或更换设备返回同一结果。
- 兑奖时锁定卡片与账户，金币入账、流水和卡片状态在同一事务提交。
- 所有金币变动都有不可删除的账本记录，记录变动前后余额、原因和关联对象。

## 3. 首版 API

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/api/v1/auth/register` | 注册并创建会话，初始发放 1000 金币 |
| POST | `/api/v1/auth/login` | 登录并创建会话 |
| POST | `/api/v1/auth/logout` | 注销当前会话 |
| GET | `/api/v1/me` | 当前用户和金币余额 |
| GET | `/api/v1/cards` | 可购买卡片及动态解锁状态 |
| POST | `/api/v1/cards/{code}/purchase` | 幂等购卡并锁定结果 |
| GET | `/api/v1/shop` | 当前永久道具等级、效果、下一级价格和余额影响 |
| POST | `/api/v1/shop/{code}/upgrade` | 幂等购买下一级永久道具 |
| GET | `/api/v1/tickets` | 当前用户卡片列表 |
| PATCH | `/api/v1/tickets/{id}/placement` | 保存卡片所在区域、桌面坐标、旋转、层级或固定槽位 |

| GET | `/api/v1/daily` | 当日登录、洗盘子与转盘状态 |

## 4. 账户与认证

- 用户名首版为 3–32 个字符，允许中文、英文字母、数字和下划线，唯一且不可重复。
- 密码为 8–72 个 UTF-8 字节，使用 Argon2id 和每个账号独立随机盐保存。
- 会话令牌由密码学安全随机数生成；浏览器只持有原始令牌，数据库只保存 SHA-256 摘要。
- 会话通过 `HttpOnly`、`SameSite=Lax` Cookie 传递，生产环境在 HTTPS 下启用 `Secure`。
- 首版会话有效期 30 天；注销后立即删除服务端会话。

## 5. 金币一致性

- 金币使用有符号 64 位整数，业务层禁止负余额。
- 扣款使用事务内 `SELECT ... FOR UPDATE` 锁定账户行。
- 发奖必须先锁定卡片，只有 `scratched` 状态的中奖卡可转为 `redeemed`。
- `coin_ledger.idempotency_key` 全局唯一，重复请求不能生成第二笔账。
- 排行榜从账户余额生成；高流量阶段写入 MySQL 后异步刷新 Redis 有序集合。

## 6. 刮刮卡实现

《零钱小票》售价 50 金币。基础好运下五档权重为头奖 5%、一等奖 10%、二等奖 20%、三等奖 30%、未中奖 35%。服务端先抽奖档，再以中奖档内 5% 的概率生成三同，否则生成两同；未中奖生成三个不同图案。好运等级按产品文档在基础概率和满级概率间插值。

卡片数据库只保存最终档位、奖励金额、图案和购卡时好运等级。概率配置可以版本化升级，但历史卡片结果永远不随配置变化。

第 2–6 款分别实现三同、横线三同、目标矿石计数、燃料和、最高价值打捞物判奖。所有开奖结果均在购卡或转盘创建卡片时由服务端生成，前端仅负责展示和刮层交互。第 7、8 款暂不开放。

## 7. 每日恢复闭环

- 登录奖励、洗盘子、免费转盘按 `Asia/Shanghai` 自然日独立刷新，次数不跨日累计。
- 洗盘子需要先创建服务端动作，再由玩家按住拖动擦除盘面残渣；前端达到 68% 清洁度才提交结算，服务端同时校验最短 3 秒、每日最多 5 次和幂等金币流水。
- 转盘按当前余额生成第 1–6 款可抽池，基础权重为 `30/22/16/12/8/6`，移除未达门槛的卡后归一化到 10000 基点。
- 转盘事务同时锁定用户与每日状态、保存卡池快照、创建 `price_paid=0` 的免费卡并消耗次数；重复请求只能返回同一张卡。

## 9. 桌面状态与一致性

- 活跃卡片只能位于 `tray`（购卡托盘）、`desk`（自由桌面）或 `slot`（固定卡槽）之一；已兑奖和已丢弃卡不再出现在活跃列表。
- 自由桌面保存 0–1 归一化坐标、-8° 至 +8° 旋转角及层级，因此同一布局可在 PC 和移动端复用。
- 每个用户最多使用 10 个固定槽位，数据库唯一约束和事务共同防止同一槽位被并发占用；固定中的卡不能丢弃。
- 中奖卡拖入兑奖区后仍走原有服务端幂等兑奖事务；未刮卡或未中奖卡只提示并留在桌面，不改变金币。
- 垃圾桶采用前端 5 秒延迟提交：撤销时不调用丢弃接口，计时结束才写入服务端；接口仍会校验卡片归属、状态和固定保护。
- 垃圾桶与固定卡槽分别是 100、500 虚拟金币的一次性永久商品；前端显示锁定状态，MySQL 与内存存储均在写操作处再次校验所有权，不能依靠绕过界面使用。
- 新购卡和免费转盘卡默认进入购卡托盘，玩家明确放置后才进入自由桌面。

## 10. 永久道具升级

- 好运从 0 级开始，最高 10 级；服务端按购卡时的好运等级生成结果，升级不会改变已经购买的卡。
- 刮奖范围默认 1 级，最高 10 级；等级由服务端持久化，前端按等级调整 Canvas 刮片半径，不改变开奖数据。
- 商店接口同时返回卡 1–6 在当前与下一好运等级下的每档真实概率和理论返奖率；展示值直接由开奖权重与奖励配置计算，避免文档和实际逻辑漂移。
- 升级配置和价格由服务端统一返回，客户端不提交价格或目标等级，只提交道具编码和幂等键。
- MySQL 升级事务依次锁定用户、检查幂等记录、校验当前等级、扣减余额、更新等级，并写入 `item_upgrades` 与 `coin_ledger`。
- 同一幂等键重复请求返回第一次升级结果，不重复扣款；不同设备并发升级导致等级过期时返回冲突并要求刷新。
- 商店会计算升级后余额，并列出因余额下降而暂时重新锁定的卡片；不提供充值或真实货币入口。
